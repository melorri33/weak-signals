# Weak Signals

Сервис ищет **зарождающиеся технологии (слабые сигналы)** по свободному запросу: собирает статьи,
препринты, патенты и новости из открытых источников, отсеивает зрелое, хайп и шум и возвращает
топ-15 ранних технологий с уверенностью модели, объяснением и ссылками на источники.

Кейс Газпромбанк.Тех. Контекст проекта и правила работы команды — в [CLAUDE.md](CLAUDE.md).

## Что уже работает

Конвейер целиком проходит в консоли. Часть шагов пока заглушки (они честно помечены в логе
прогона строками «… ещё не готов — работаю на заглушке»):

| Шаг | Состояние |
| --- | --- |
| Расширение запроса в поисковые фразы | локальная LLM, при недоступности — фразы из самого запроса |
| Сбор источников и статистика по терминам | настоящие источники: техноновости, OpenAlex, arXiv, Hacker News, Википедия |
| Хранилище | PostgreSQL; база не поднята — конвейер работает, но прогон не переживёт перезапуск |
| Выделение кандидатов | заглушка на правилах (LLM + эмбеддинги — дальше по плану) |
| Признаки и скоринг | CatBoost со SHAP-объяснением |
| Уровни доверия и правила отсева | настоящие: `config/trust_domains.yaml`, `config/filter_rules.yaml` |
| Карточки сигналов | источники настоящие (только из собранных документов), тексты — заглушка |
| API и интерфейс | FastAPI (`POST /search`, `GET /search/{run_id}`) и Streamlit |

## Запуск с нуля

Нужны: macOS или Linux, Python 3.11, Docker, ~10 ГБ на диске под модель.

### 1. Код и зависимости

```bash
git clone <адрес репозитория> && cd weak-signals
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # править не обязательно, значения по умолчанию рабочие
```

### 2. Модель: локально или в облаке

Проект работает с тремя провайдерами, выбор — переменная `LLM_PROVIDER`:

| `LLM_PROVIDER` | Где считает | Когда выбирать |
| --- | --- | --- |
| `ollama` | своя машина, бесплатно | есть видеокарта (проверяли на RTX 3060) |
| `yandexgpt` | облако Яндекса, по токенам | нет видеокарты и для стенда жюри |
| `gigachat` | облако Сбера, по токенам | то же; вторая облачная модель для сравнения |

На процессоре без видеокарты локальная модель не успевает: один вызов на пачку из 8 документов
занял **143 с** (`qwen3:8b`, MacBook Air M1 в контейнере), а таких пачек в прогоне десятки.
Поэтому на такой машине — облако.

#### Вариант А: локальная модель (Ollama на хосте)

```bash
# macOS: brew install ollama && brew services start ollama
# Linux: curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3:8b            # ~5 ГБ — рабочая модель
ollama pull qwen3:4b            # ~2,5 ГБ — по желанию: вдвое быстрее, но качество ниже
ollama list                     # модель должна быть в списке
```

Если в системе настроен HTTP-прокси, добавь `localhost` в `NO_PROXY` — иначе запросы к Ollama
пойдут через прокси. Наш код к Ollama ходит мимо прокси сам, а вот `curl` придётся подсказать:
`curl --noproxy '*' http://localhost:11434/api/tags`.

#### Вариант Б: облачная модель YandexGPT

ТЗ разрешает облако только из своего списка; у Яндекса это YandexGPT Lite 5 и Pro 5/5.1.
Другую модель код не пустит — упадёт с объяснением ещё до первого запроса.

1. В [Yandex Cloud](https://console.cloud.yandex.ru) создай каталог, сервисный аккаунт с ролью
   `ai.languageModels.user` и API-ключ для него.
2. Впиши в `.env`:

```bash
LLM_PROVIDER=yandexgpt
LLM_MODEL=yandexgpt-5-lite      # или yandexgpt-5-pro, или yandexgpt-5.1
YANDEX_API_KEY=…
YANDEX_FOLDER_ID=…              # идентификатор каталога
```

Проверка: `curl -s localhost:8000/health` покажет `"llm_available": true`. Ollama при этом не нужна.
Запросы к облаку идут так же, как к локальной модели, и так же попадают в журнал вызовов моделей
(требование ТЗ): в выдаче будет `provider: yandexgpt` и имя модели.

#### Вариант В: облачная модель GigaChat

Из списка ТЗ — GigaChat 2 Lite, Pro и Max (`GigaChat-2`, `GigaChat-2-Pro`, `GigaChat-2-Max`).

1. В [личном кабинете](https://developers.sber.ru/studio) создай проект GigaChat API →
   «Настройки API» → «Получить ключ». Ключ показывается один раз.
2. Серверы Сбера подписаны НУЦ Минцифры — скачай корневой сертификат:
   `curl -o data/certs/russian_trusted_root_ca_pem.crt https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`
3. Впиши в `.env`:

```bash
LLM_PROVIDER=gigachat
LLM_MODEL=GigaChat-2
GIGACHAT_CREDENTIALS=…          # «Authorization Key»
GIGACHAT_CA_BUNDLE=data/certs/russian_trusted_root_ca_pem.crt
```

### 3. База данных

```bash
docker compose up -d db
docker compose ps               # состояние healthy
```

База пока нужна только для хранения документов и прогонов (модуль `src/storage`); конвейер
работает и без неё.

### 4. Прогон

```bash
python -m src.pipeline.cli "перспективные решения в финтехе"
```

Полезные флаги:

```bash
python -m src.pipeline.cli "квантовые вычисления в банках" --json out.json   # сохранить весь SearchResult
python -m src.pipeline.cli "финтех" --json > result_fintech.json             # JSON в stdout, без отчёта
python -m src.pipeline.cli "финтех" --no-progress                           # без строк прогресса
```

JSON прогона нужен для проверки «как у жюри» (`python -m src.model.eval_search result.json`): она считает,
сколько технологий датасета нашлось на шагах «документы → кандидаты → топ-15». Файл датасета есть только
у владельца ядра, поэтому JSON прогонов по шести областям отправляем ему.

Выдача в консоли: поисковые фразы → топ сигналов (уверенность, описание, преимущество, кейс,
почему ранний сигнал, ключевые предикторы, источники со ссылками, датой, типом, языком и уровнем
доверия) → исключённые кандидаты с причиной → список вызовов моделей.

### 5. API

```bash
uvicorn src.api.main:app --reload
```

Полный прогон идёт минуты, поэтому `POST /search` не ждёт результата: он заводит прогон и сразу
отдаёт `run_id`, а выдачу забирают по `run_id`.

| Запрос | Что делает |
| --- | --- |
| `GET /health` | доступны ли модель и база; в `notes` — по-русски, что не поднято |
| `POST /search` `{"query": "..."}` | запускает прогон, отвечает `202` и `SearchResult` со `status='running'` |
| `GET /search/{run_id}` | текущее состояние: `stage` — шаг конвейера, `status='done'` — выдача готова |
| `GET /signal/{run_id}/{candidate_id}` | карточка одного сигнала из выдачи |

```bash
curl -s localhost:8000/health
run=$(curl -s -X POST localhost:8000/search -H 'content-type: application/json' \
      -d '{"query":"перспективные решения в финтехе"}' | python -c 'import json,sys; print(json.load(sys.stdin)["run_id"])')
curl -s localhost:8000/search/$run | python -m json.tool | head -20
```

Прогон на ноутбуке идёт один за раз: локальная модель одна, и два прогона одновременно уводят
машину в swap. Пока прогон не закончился, второй `POST /search` отвечает `429` с номером текущего.
Документация эндпоинтов со схемами — на `/docs`.

## Запуск в Docker

Всё приложение целиком — база, API и интерфейс:

```bash
cp .env.example .env            # заполни доступы к модели
docker compose up -d --build
docker compose ps               # db и api — healthy
```

| Что | Где |
| --- | --- |
| API | http://localhost:8000 (документация — `/docs`) |
| Интерфейс | http://localhost:8501 |
| База | `localhost:5432`, том `db-data` |
| Прогоны и кэш ответов модели | папка `./data` на хосте, общая у `api` и `ui` |

Консольный прогон в контейнере:

```bash
docker compose exec api python -m src.pipeline.cli "перспективные решения в финтехе"
```

**Где живёт модель.** `localhost` внутри контейнера — это сам контейнер, поэтому для Docker есть
отдельная переменная `OLLAMA_URL_IN_DOCKER`. Приложение само видит, что работает в контейнере,
и берёт адрес из неё:

| Модель | `.env` |
| --- | --- |
| Ollama на хосте (по умолчанию) | `OLLAMA_URL_IN_DOCKER=http://host.docker.internal:11434` |
| Ollama в контейнере | `docker compose --profile local-llm up -d`, затем `OLLAMA_URL_IN_DOCKER=http://ollama:11434` и `docker compose exec ollama ollama pull qwen3:8b` |
| Облако | `LLM_PROVIDER=yandexgpt` и ключи — адрес Ollama не нужен |

`DATABASE_URL` внутри compose подставляется сам (хост `db` вместо `localhost`), значение из `.env`
для контейнеров не используется — оно нужно процессам на хосте.

Пересобрать образ после правки зависимостей: `docker compose build --no-cache api`.
Зависимости образа — `docker/requirements-app.txt`: подмножество `requirements.txt` без обучения
и отчётов, иначе в образ приезжают torch и соседи (за этим следит `tests/test_requirements.py`).

## Настройки

Все параметры — через `.env` (образец в [.env.example](.env.example)):

| Переменная | Зачем | По умолчанию |
| --- | --- | --- |
| `LLM_PROVIDER` | `ollama` — локально, `yandexgpt` или `gigachat` — облако из списка ТЗ | `ollama` |
| `LLM_MODEL` | модель: `qwen3:8b` для Ollama или `yandexgpt-5-lite` для облака | `qwen3:8b` |
| `OLLAMA_URL` | адрес Ollama для процессов на хосте | `http://localhost:11434` |
| `OLLAMA_URL_IN_DOCKER` | адрес Ollama для контейнеров | `http://host.docker.internal:11434` |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | доступ к облаку при `LLM_PROVIDER=yandexgpt` | пусто |
| `GIGACHAT_CREDENTIALS`, `GIGACHAT_CA_BUNDLE` | доступ к облаку при `LLM_PROVIDER=gigachat` | пусто |
| `LLM_CACHE` | кэшировать ответы модели в `data/llm_cache` (`0` — выключить) | `1` |
| `API_PORT`, `UI_PORT` | порты API и интерфейса на хосте | `8000`, `8501` |
| `EMBED_MODEL` | модель эмбеддингов для склейки кандидатов | `BAAI/bge-m3` |
| `DATABASE_URL` | подключение к PostgreSQL | `postgresql+psycopg://weak:weak@localhost:5432/weak_signals` |
| `MAX_DOCUMENTS` | сколько документов собираем максимум | `500` |
| `SOURCE_TIMEOUT_S`, `COLLECT_BUDGET_S` | таймаут источника и бюджет всего сбора | `15`, `60` |

## Если что-то не работает

| Симптом | Причина и что делать |
| --- | --- |
| `Ollama недоступна на http://localhost:11434` | не запущен Ollama: `brew services start ollama` или `ollama serve` |
| `Модель … не скачана` | `ollama pull qwen3:8b` (или та, что стоит в `LLM_MODEL`) |
| В логе «… ещё не готов — работаю на заглушке» | так и задумано: модуль ещё пишется, конвейер идёт дальше |
| Прогон падает на `db` | база не нужна для CLI; если нужна — `docker compose up -d db` |
| Прогон идёт дольше 5 минут | выгрузи лишние модели (`ollama stop qwen3:4b`) или поставь `LLM_MODEL=qwen3:4b` |
| API отвечает `429` | прогон уже идёт, номер текущего — в тексте ошибки; дождись его или посмотри `GET /health` |
| В `GET /health` `database_available: false` | `docker compose up -d db`; без базы прогоны живут только в памяти сервера |
| В контейнере `llm_available: false`, а на хосте модель работает | проверь `OLLAMA_URL_IN_DOCKER`: для Ollama на хосте это `http://host.docker.internal:11434`, для сервиса из профиля — `http://ollama:11434` |
| `Провайдер '…' не поддерживается` | в `LLM_PROVIDER` опечатка: бывает `ollama` или `yandexgpt` |
| `Модель '…' не из списка ТЗ` | облачные модели разрешены только из перечня организаторов — смотри список в тексте ошибки |
| `Для LLM_PROVIDER=yandexgpt нужны YANDEX_API_KEY и YANDEX_FOLDER_ID` | заполни оба в `.env` |
| Облако отвечает `401` | ключ не от того каталога или роль не `ai.languageModels.user` |
| Кандидаты выглядят как заголовки новостей | модель не успела в бюджет шага и сработала запасная нарезка — смотри «Сколько времени занимают шаги» |

### Сколько времени занимают шаги

Замеры на MacBook Air M1 (16 ГБ). Расширение запроса прогонялось по шести областям датасета:

| Модель | Скорость генерации | Один вызов `expand_query` | Качество фраз |
| --- | --- | --- | --- |
| `qwen3:8b` | ~4,8 токенов/с | 60–92 с | 18 годных фраз во всех шести областях |
| `qwen3:4b` | ~8,8 токенов/с | 25–31 с | в двух областях из шести мусор: шаблоны и выдуманные термины |

Поэтому рабочая модель — **`qwen3:8b`**: расширение запроса делается один раз за прогон, а от его
качества зависит, найдётся ли технология вообще. На слабой машине можно поставить
`LLM_MODEL=qwen3:4b` — прогон станет быстрее, но часть запросов даст плохие фразы.

**На процессоре локальная модель не успевает.** Замер в контейнере на MacBook Air M1: один вызов
`extract_candidates` на пачке из 8 документов — **143 с** на `qwen3:8b`, при собственном бюджете шага
`BUDGET_S = 150` с (`src/pipeline/candidates.py`). То есть успевает ровно одна пачка из восьми
документов, а дальше срабатывает запасная нарезка названий из заголовков — в топ-15 попадают
«TechCrunch Mobility» вместо технологий, и по выдаче это выглядит не как таймаут, а как плохое
качество. Полный прогон: **1400 с** на ноутбуке без видеокарты против **444 с** на RTX 3060 (14B,
холодный прогон без кэша: карточки 182 с, кандидаты 134 с, сбор 52 с).

Вывод: без видеокарты прогон делаем на облачной модели (`LLM_PROVIDER=yandexgpt`). Бюджеты шагов
(`CANDIDATES_BUDGET_S = 180`, `CARDS_BUDGET_S = 300` в `src/pipeline/run.py`) рассчитаны на
видеокарту — для облака их ещё будем перемерять.

Время каждого шага пишется в лог прогона (строки «Шаг … из … с бюджета») — по ним видно, где
конвейер упирается в бюджет. Держать в памяти сразу две модели на 16 ГБ нельзя: машина уходит
в свап, и обе замедляются. Выгрузить лишнюю: `ollama stop qwen3:4b`.
